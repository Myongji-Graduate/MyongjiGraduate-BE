## 1. 목표와 자료의 적용 범위

**개인 수강내역 캐시를 유지하면서 동시 조회·롤백 정합성, 버전 전환, 장애 대응을 개선한다.**
캐시 제거를 기본안으로 둔 이전 계획을 대체한다. 공통 과목·졸업요건 공유 캐시는 유지한다.

| 작업 단위 | 포함 내용 | 순서·완료 기준 |

| 성능 최적화 — 측정 후 후속 작업 | SQL·인덱스·중복 계산 최적화, CPU·메모리 상세 프로파일링 | 최소 계측에서 확인된 병목을 대상으로 진행. 캐시 정합성 수정과 계산 알고리즘 변경을 동시에 섞지 않음 |

같이 고려하는 항목을 모두 하나의 PR로 묶을 필요는 없다. 캐시 개선은 검증 기반·정합성
구현·장애 및 전환 검증으로 나눌 수 있지만, 전체 완료 판정은 P0~P5의 근거로 한다.
최소 계측은 수정 전 기준선을 확보할 때부터 시작하며 P4는 수정 후 비교 결과를 정리하는 단계다.
ArchUnit과 AI 장애 격리는 별도 작업 범위와 완료 기준을 둔 것이며 아직 구현하지 않았다.

Shadow 비교는 같은 데이터 revision의 DB 결과를 기준으로 한다. 기존 캐시 응답을
정답으로 간주하거나 사용자 쓰기를 두 번 수행하지 않는다. 실제 운영 shadow 도입은
합성 환경 검증 이후 별도로 검토한다. Redis 장애 때 DB로 요청이 몰리는 현상은 이
캐시 계획에서 측정하고, AI 호출의 자원 격리와는 별개로 필요한 동시성 제한을 판단한다.

대조군 2건을 포함한 12건의 통과는 결함 재현 성공이다. 계산 경계는 실제 캐시 조회를
호출하는 probe였으므로 전체 졸업 계산·요약 저장의 정답성까지 검증한 것은 아니다.

수정 후 계약:

1. 변경 성공 후 새 트랜잭션으로 시작한 조회는 커밋된 수강내역을 읽는다.
2. 변경 트랜잭션 안의 계산은 같은 DB 트랜잭션에서 자기 INSERT/DELETE를 포함해 읽는다.
3. 롤백된 목록과 데이터 revision은 공유 캐시에 게시하지 않는다.
4. 오래된 조회가 늦게 저장되더라도 새로운 데이터 revision의 조회에는 사용되지 않는다.
5. 개인 캐시 접근 실패는 가능한 경우 DB 조회로 복구한다. DB 실패까지 성공으로 숨기지 않는다.
6. 권한 검사, API 응답 필드와 학사 정책을 보존한다. 일반 졸업/학점 조회는 계산만 수행하도록 변경한다.

변경과 겹쳐 시작한 읽기는 이전의 일관된 DB 스냅샷을 볼 수 있다. 모든 기존 요청이
즉시 최신 커밋을 보도록 격리 수준을 바꾸는 작업은 아니다. 같은 학생의 동시 쓰기나
요약 저장에 별도 문제가 발견되면 캐시 결함과 구분해 검증한다.

## 3. 설계안

### A. 쓰기 트랜잭션의 조회와 캐시 게시 분리

- 수강내역을 변경하는 트랜잭션에서는 개인 캐시 읽기·채우기를 우회한다.
  재계산은 새 트랜잭션을 열지 않고 기존 쓰기 트랜잭션의 DB 상태를 읽는다.
- 추가·삭제·재업로드의 변경 진입점에서 이 규칙이 빠짐없이 적용되게 한다.
  메서드의 readOnly 선언만 보고 판단하지 않고 실제 참여 중인 트랜잭션과 AOP 순서를 검증한다.
- 읽기용 트랜잭션에서 얻은 캐시 적재 후보는 성공적으로 종료한 뒤 게시한다.
  쓰기 트랜잭션에서 만든 미커밋 목록을 게시 대상으로 재사용하지 않는다.
- 커밋 후 정리나 게시가 실패해도 이미 성공한 DB 커밋을 실패한 것처럼 응답하지 않도록 한다.
  정합성은 다음 B의 DB revision 선택으로 보장하고, 실패한 Redis 작업은 관측한다.

Spring의 [TransactionAwareCacheDecorator 문서](https://docs.spring.io/spring-framework/docs/6.1.13/javadoc-api/org/springframework/cache/transaction/TransactionAwareCacheDecorator.html)는
일부 캐시 쓰기·삭제의 커밋 후 실행을 설명한다. 이것만으로 늦은 재적재를 막거나
쓰기 중 이전 캐시를 읽는 문제까지 해결한다고 판단하지 않는다. 이 한계 판단은 이번
재현과 실행 순서 분석에 따른 것이다.

### B. 데이터 revision으로 늦은 재적재 격리

구현 방식은 **DB에 학생별 수강내역 revision을 두고 목록 변경과 함께 커밋하는 것**이다.
`user.taken_lecture_revision`과 마이그레이션(당시 V12, 현재 V14)으로 구현했으며 기존 변경 진입점을 확인했다.

v2 단계 키: `takenLectures:v2:{namespace}:{userId}:{dataRevision}`

- `v2`: 직렬화·캐시 계약을 구분하는 형식 버전. 배포 때마다 무조건 증가시키는 값이 아니다.
- `dataRevision`: 해당 학생의 수강내역 변경을 구분하는 DB 값. 배포 ID로 대체하지 않는다.
- 일반 조회는 DB에서 revision을 확인하고 해당 revision의 캐시만 조회한다.
- 캐시 miss이면 revision과 목록을 **같은 DB 스냅샷**에서 얻는다. 서로 다른 연결이나
  트랜잭션의 값을 조합하지 않는다. JPA의 오래된 엔티티 값과 최신 SELECT 혼합도 검증한다.
- 목록의 추가·삭제·전체 교체와 revision 증가는 같은 트랜잭션에서 이루어져야 한다.
  동시 쓰기에서 revision 증가를 잃지 않도록 DB 원자 증가 또는 행 잠금 방식을 검증한다.
- 쓰기 트랜잭션이 롤백되면 revision도 함께 롤백된다. 쓰기 중 캐시 게시가 금지되어 있어
  롤백된 revision 번호가 나중에 사용되더라도 이전 미커밋 목록과 충돌하지 않아야 한다.
- 과거 revision으로 시작한 reader는 그 revision의 키에만 저장한다. 이전 키는 TTL로
  만료시킨다. 최신성 판단을 Redis의 별도 current 포인터나 캐시 삭제 성공에 의존하지 않는다.
- payload는 revision과 조회 결과를 복원할 불변 스냅샷으로 구성한다. 공유 과목 정보 등
  목록 외의 가변 데이터가 포함된다면 변경 의존성을 추적하거나 해당 필드를 분리한다.

예: reader가 revision 10의 3학점을 읽은 뒤 writer가 6학점과 revision 11을 커밋하면,
reader의 늦은 저장은 `...:10`에만 들어간다. 이후 새 조회는 DB revision 11을 확인하므로
`...:10`을 선택하지 않는다. 롤백이면 목록과 revision 모두 이전 상태로 남는다.

이 방식은 캐시 hit에도 revision 조회 DB 비용이 든다. 전체 목록 조회를 줄이는 이득과
추가 비용을 함께 측정한다. 캐시 유지 자체를 성능 개선이 입증된 것으로 보고하지 않는다.

### C. 개인 캐시 장애 대응

- 개인 캐시의 읽기·역직렬화 실패는 miss로 취급하고 DB에서 읽는다.
- 캐시 저장 실패는 정상 DB 조회 결과를 버리지 않고 오류 지표에 기록한다.
- Redis timeout과 반복 실패 시 짧은 우회 기간, 복구 확인 요청을 설계·검증한다.
  기존 공유 캐시 구현은 참고하되 개인 캐시까지 이미 보호한다고 가정하지 않는다.
- DB fallback 증가 시 연결 풀·동시 요청 한계를 측정하고, 과부하 시 제어된 실패 조건을 정한다.
- 현재 revision을 확인할 DB 자체가 실패하면 오래된 개인 캐시를 최신이라고 반환하지 않는다.
- 개인 캐시 장애와 인증 등 다른 Redis 기능 장애를 구분한다.

## 6. v2 최초 구현 검증과 당시 판단 (2026-10-27)

### 검증 범위

- 기존 진단 12건으로 결함을 다시 재현한 뒤 기대값을 정상 계약으로 바꿨다.
- 실제 Spring 트랜잭션 프록시·MySQL 8.4.8·Redis 7.4를 사용했다. 두 독립 앱 컨텍스트,
  별도 JVM의 실제 변경 서비스/계산/요약 저장과 커밋 후 `Runtime.halt(0)`도 포함한다.
- 동시 조회/롤백 각 5회, 늦은 과거 revision 게시, revision 재사용, 같은 학생 동시 변경,
  삭제·재업로드, 소유권 검사, 현재 과목/사용자 정보, 읽기 전용 조회를 확인했다.
- Redis 응답 지연 1.2초, 명령 timeout, 실제 재시작/재연결, 잘못된 JSON, 조회·저장 예외,
  복구 후 재적재, 비트랜잭션/쓰기/READ COMMITTED 우회를 확인했다.
- 실제 계산기는 합성 철학과 일반 학생과 자유선택 과목을 사용하고, 정책 포트는 고정된
  빈 합성 정책으로 대체했다. 운영 정책 전체의 정확성 검증은 아니다. 기존 학사 정책 테스트는 별도로 실행한다.
- 실제 앱 HTTP/auth를 포함한 운영 부하 실험은 아니다. DB 자체 장애는 loader 실패의 전파를 단위 테스트로 확인한다.
  MySQL 서버 단절, Redis Cluster/Sentinel 장애 전환, 실제 운영 용량은 검증하지 않았다.
- Redis 전용 제한은 개인 수강내역 캐시 접근에만 적용된다. 인증/다른 Redis 기능까지 장애 대응을 보장하지 않는다.

### 성능 실험 해석

`TakenLectureCacheBenchmarkIntegrationTest`는 수강내역 30/60/120개와 읽기 동시성 1/4/8을 사용한다.
네 warm 경로는 각 조건에서 순서를 바꾸어 3회, 매회 32요청으로 비교했다. cold burst와
Redis 오류 fallback은 조건별 1회, 혼합 부하는 조건별 3회(32조회 + 실제 추가/삭제 8회)를 실행했다.
혼합 부하의 동시성은 reader 수이며 별도의 writer 1개가 함께 동작한다.

- 구 캐시는 기존 JDK 직렬화 형식과 동일한 cache-aside hit를 재현한 비교군이다. 구 앱 전체를 별도 배포한 성능 비교는 아니다.
- 원본 MySQL은 최종 정답 비교 기준이다. 신형식은 목록 ID, 사용자 ID, 과목 ID/이름/학점/폐강/대체 코드,
  수강년도/학기/시각을 정규화해 대조했다. shadow는 DB 결과를 반환하며 membership 불일치를 별도 계수한다.
- 새 warm hit는 수강목록 join 자체를 생략하지만 사용자·revision·카탈로그의 SQL 3회를 실행한다.
  DB 직접 경로는 사용자·수강목록 join의 2회다. 구 warm hit의 SQL은 0회다.
- **정합성 개선과 성능 개선을 동일시하지 않는다.** 이 소규모 로컬 실험에서 v2를 활성화할 성능상 이득은 확인되지 않았다.
  지연 증가를 수용할지, 카탈로그/조회 비용을 별도 작업으로 줄일지 검토한 후 운영 `on`을 선택한다.
- DB 대기는 요청 시작 시점의 waiter 표본과 Hikari 획득 시간이다. CPU는 테스트 JVM 프로세스 시간,
  메모리는 heap 사용량 차이이므로 GC/계측 영향을 받는다. DB/Redis 서버 CPU나 정확한 할당량을 의미하지 않는다.
- Redis 메모리는 테스트 키별 MEMORY USAGE와 직렬화 길이다. 이전 revision 키가 TTL 동안 남으므로
  사용자당 총 메모리는 revision 변경 빈도에 비례해 늘 수 있다. 이 실험은 단일 revision 크기 비교다.

검증 명령 `test jacocoTestReport` 성공: **813건 중 811건 통과, 실패 0, 오류 0, 기존 opt-in 벤치마크 2건 제외**.
새 캐시 관련 41건(정합성 통합 24 + 단위 12 + 설정 4 + 성능 실험 1)은 모두 실행·통과했다.
별도 [비활성 가드 검증](reviews/dev121-disabled-guard-20261027.json)은 존재하지 않는 Docker socket과 false 플래그로 실행하여
컨테이너 실험이 건너뛰어지는 것을 확인했다. 전체 결과는 [실행 집계/소스 해시](reviews/dev121-verification-20261027.json),
성능 원시 집계는 [153개 조건별 측정값](reviews/dev121-benchmark-20261027.json)에 보관했다.

### 배포와 되돌림 절차

아래는 실행하지 않은 운영 절차다. 스키마와 코드의 단계적 전환을 위해 기본 모드를 `off`로 둔다.
캐시 구현은 유지하며 `on`에서 실제 hit를 검증했다.

1. 대상 DB·프로파일·Flyway 상태를 확인한다. V14는 사용자별 revision을 기본값 0으로 추가하며 V15는 과목 revision과 트리거를 만든다.
   현재 prod/local 설정의 Flyway 활성화 여부를 확인하고 기존 마이그레이션 체계를 따른다.
   `ddl-auto=update`나 앱 시작을 마이그레이션 실행 확인의 대체 수단으로 쓰지 않는다.
   DEV-121을 먼저 배포하며 V11 → V14/V15 순서로 적용한다. V12/V13이나 DEV-116 병합은 요구하지 않는다.
   후속 DEV-116의 미적용 파일은 그때의 최신 적용 버전 이후로 번호를 정리한다. 이 작업에서 DEV-116을 수정하지 않는다.
   [배포 준비](DEV-121_CACHE_DEPLOYMENT.md)를 따르고, 최종 병합 대상과 운영 이력을 다시 확인한다.
2. 구 앱으로 가는 트래픽을 중지하고 진행 중인 조회·변경 요청을 비운 뒤 revision-aware 코드로 전환한다.
   이 구현은 구 캐시 키를 갱신하지 않으므로 구 reader와 신 writer를 동시에 서비스하는 rolling 전환은 지원하지 않는다.
   신 코드의 모든 인스턴스는 먼저 `TAKEN_LECTURE_CACHE_MODE=off`로 실행한다.
   직접 SQL, 배치, 다른 서비스 등 모든 목록 writer가 같은 트랜잭션에서 revision을 갱신해야 한다.
3. 환경별 새 `TAKEN_LECTURE_CACHE_NAMESPACE`(예: `prod-dev121-20261027-a`)를 선택한다.
   구 writer가 모두 사라진 뒤 `TAKEN_LECTURE_CACHE_MODE=shadow`로 전환한다.
   잘못된 구 writer가 revision 없이 수정하면 `on`이 과거 목록을 반환할 수 있음을 합성 테스트로 확인했다.
   shadow는 같은 revision의 DB를 읽어 불일치를 드러내며, 구 캐시 결과를 정답으로 삼지 않는다.
4. `mismatch=0`, 오류·지연·DB 획득 대기와 추가 SQL 비용을 검토한다. 이 실험에서 관측된 성능 악화를
   해결하거나 수용하기 전에는 운영 `on`을 자동 권고하지 않는다. 통과하면 같은 namespace에서 `on`으로 전환한다.
   한글 사용자 정보나 학생 식별자를 metric label에 넣지 않는다.
5. 구 `takenLectures::...`는 기존 TTL(10분), v2의 이전 revision 키는 10분 TTL로 만료시킨다.
   전환을 위해 `FLUSHALL`/`FLUSHDB`를 하지 않는다. 합성 환경에서만 두 형식을 병행 적재·비교했다.
   운영에서 구형식 dual-write를 계속하거나 구형식을 fallback으로 읽는 경로는 없다.
6. 불일치·장애·부하 증가 시 revision-aware 코드를 유지한 채 `off`로 전환한다.
   재활성화할 때는 원인을 해결하고 새 namespace에서 shadow를 다시 확인한다. 코드 되돌림이 필요하면
   revision 갱신과 캐시 우회를 유지하는 호환 버전으로 되돌린다. 결함이 있는 구 `@Cacheable` 경로로 자동 복귀하지 않는다.
   컬럼은 additive 상태로 남기며 즉시 DROP하지 않는다.
7. 과거 잘못 저장된 `user.taken_credit`/졸업 여부/`completed_credit`는 자동 일괄 복구되지 않는다.
   현재 조회는 새로 계산하지만 저장된 과거 요약의 영향 조사·재계산은 대상과 근거를 정한 별도 작업이다.

관측 지표는 `takenlecture.cache{outcome=hit|miss|shadow|mismatch|error|fallback|bypass|transaction_bypass|saturated|load|put|invalid_payload}`와
`takenlecture.cache.load` timer다. outcome 외에 사용자/과목별 label을 만들지 않는다.
`transaction_bypass`는 mode off 또는 안전하지 않은 트랜잭션 경계, `bypass`는 장애 우회/포화 경로다.
`hit`은 payload 선택 지표이며 과목이 사라진 경우 `invalid_payload` 뒤 DB fallback이 추가로 발생할 수 있다.

### 재실행

새 일회용 컨테이너만 사용한다. 테스트는 이미 받은 `mysql:8.4.8`·`redis:7.4-alpine` 이미지에 한해 실행되며,
없는 이미지를 자동 pull하지 않는다. 아래 환경 변수는 실행할 때만 지정한다.

```sh
RUN_TAKEN_LECTURE_CACHE_REPRODUCTION=true \
RUN_TAKEN_LECTURE_CACHE_BENCHMARK=true \
./gradlew test jacocoTestReport --no-daemon --no-build-cache
```

Docker Desktop 로컬 환경에서는 `DOCKER_HOST=unix:///Users/jinhyeon/.docker/run/docker.sock`,
`TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock`, `TESTCONTAINERS_HOST_OVERRIDE=127.0.0.1`도 사용했다.
현재 CI는 이 두 opt-in 환경 변수를 자동 설정하지 않는다. 일반 단위/설정/API 회귀 테스트는 기본 test에 포함되고,
컨테이너 정합성 실험과 benchmark는 위 명령으로 명시적으로 실행한다. 벤치마크 결과는
`build/dev121/synthetic-cache-benchmark.json`, 테스트 보고서는 `build/reports/tests/test/index.html`에 생성된다.
