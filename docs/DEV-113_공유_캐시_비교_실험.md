# DEV-113: Redis 공유 캐시와 Caffeine 비교 실험

- 측정일: 2026-09-14 (KST)
- 브랜치 / 운영 코드 기준 커밋: `feature/DEV-113` / `529003b`
- 운영 DB에 접속하지 않고 Testcontainers의 독립 MySQL·Redis에서 실행했다.
- 공유 캐시는 테스트 전용 어댑터로 실제 구현하여 HTTP 경로에 연결했다. 운영 코드에 적용하거나 배포하지 않았다.
- `build.gradle`에는 Caffeine 3.1.8의 테스트 의존성만 추가했다. 운영 런타임 의존성은 바뀌지 않는다.

## 결론

공유 마스터 캐시는 이번 데이터에서 반복 SQL을 64.3% 줄였다.
그러나 Redis와 Caffeine 중 하나가 모든 지표에서 우세하지는 않았다.

- 초당 200요청 조건에서는 Redis 공유 캐시의 평균과 p95가 더 낮았다.
- 100 VU 버스트에서는 Caffeine의 평균이 더 낮고, Redis의 회차별 p95가 더 낮았다.
- 따라서 공유 캐시 도입의 근거는 얻었지만, 운영 환경의 최적 구현을 확정한 것은 아니다.
- 현재 Redis 인프라를 활용하고 응답 지연의 상위 구간을 우선한다면 Redis 공유 캐시가 합리적인 첫 적용 후보다.
  단일 인스턴스에서 순간 부하의 평균 지연을 우선한다면 Caffeine도 비교 가치가 있다.

## 측정 결과

모든 방식에서 기존 개인 Redis 캐시(JDK 직렬화, TTL 10분)는 유지했다.
공유 캐시는 동일한 불변 스냅샷을 저장하며, TTL 24시간을 사용했다.

### 일정한 요청률

초당 200요청을 20초간 보내고, 방식별로 3회 측정했다. 각 방식 12,000요청이다.
100 VU는 미리 할당한 상한이며, 동시 실행 100개를 계속 유지한다는 뜻은 아니다.

| 방식 | 전체 평균 | 회차별 평균 범위 | 회차별 p95 범위 | SQL / 4,000요청 |
| --- | ---: | ---: | ---: | ---: |
| 기존 개인 Redis만 | 4.83ms | 4.59~5.10ms | 7.43~8.48ms | 11,200 |
| 개인 Redis + Redis 공유 | 3.77ms | 3.63~3.89ms | 5.54~6.03ms | 4,000 |
| 개인 Redis + Caffeine 공유 | 4.04ms | 3.77~4.43ms | 5.96~6.40ms | 4,000 |

평균 감소율은 Redis 공유 22.1%, Caffeine 공유 16.5%다.
요청률을 고정한 실험이므로 이 결과를 최대 처리량 개선 수치로 해석하지 않는다.

### 순간 부하

100 VU가 대기 시간 없이 총 800요청을 나누어 실행했다. 방식별 3회, 각 방식 2,400요청이다.
각 VU가 정확히 8회씩 실행하는 설정은 아니며, 전체 HTTP 요청 수와 질문 분포를 고정했다.

| 방식 | 전체 평균 | 회차별 평균 범위 | 회차별 p95 범위 | SQL / 800요청 |
| --- | ---: | ---: | ---: | ---: |
| 기존 개인 Redis만 | 132.39ms | 118.03~148.97ms | 186.75~265.23ms | 2,240 |
| 개인 Redis + Redis 공유 | 96.38ms | 89.68~103.73ms | 142.67~157.82ms | 800 |
| 개인 Redis + Caffeine 공유 | 86.34ms | 80.51~93.36ms | 153.22~183.75ms | 800 |

평균 감소율은 Redis 공유 27.2%, Caffeine 공유 34.8%다.
전체 평균은 동일 요청 수를 가진 세 회차의 평균이다. p95는 회차별 범위이며 통합 p95가 아니다.

### SQL과 콜드 캐시

기존 개인 캐시만 사용한 일정 요청률 실험에서 4,000요청당 사용자 4,000회,
공통교양 800회, 핵심교양 800회, 기초학문교양 800회, 전공 2,400회, 선택필수 정책 2,400회의 SQL이 발생했다.
공유 캐시가 준비된 후에는 두 구현 모두 사용자 조회 4,000회만 남았다. 공유 데이터 재로딩은 0회였다.

일정 요청률 실험에 앞서 캐시를 비운 상태에서 각 방식에 800요청을 보낸 결과:

| 방식 | 총 SQL | 공유 데이터 로딩 |
| --- | ---: | ---: |
| 개인 Redis만 | 2,322 | 공유 캐시 없음 |
| Redis 공유 | 909 | 서로 다른 26개 키에 대해 26회 |
| Caffeine 공유 | 909 | 서로 다른 26개 키에 대해 26회 |

이는 한 JVM 안에서의 동일 키 중복 로딩 억제를 확인한 것이다.
개인 캐시는 기존 구현을 그대로 사용하여, 콜드 상태에서는 일부 중복 수강과목 조회가 발생했다.
여러 서버를 합쳐 DB 조회가 1회로 제한된다는 의미는 아니다.

### 메모리

- 개인 Redis 캐시: 80개 키, `MEMORY USAGE` 합계 828,416바이트. 세 방식에서 동일했다.
- Redis 공유 캐시: 26개 키, 약 36KB의 추가 Redis 할당량.
- Caffeine: 26개 엔트리, 같은 값을 JDK 직렬화했을 때 페이로드 합계 28,794바이트.
- 마지막 수치는 JVM 실제 점유량이 아니다. Caffeine의 키·엔트리·객체 그래프까지 포함한 retained heap은 측정하지 않았다.
- 실행별 JVM 사용 힙, GC 횟수, 프로세스 CPU 시간도 원본 JSON에 있다. 사용 힙은 GC 시점에 영향을 받으므로 캐시 메모리 우열의 근거로 사용하지 않는다.

## 데이터와 시나리오

- 강의는 저장소 `lecture.csv`를 기존 `LectureFixture` 로더로 읽은 198개 고유 코드다.
- 공통교양 33행, 핵심교양 23행, 전공 94행, 기초학문교양 2행, 선택필수 정책 1개와 후보 7개를 기존 fixture에서 구성했다.
- 국제통상학과·데이터사이언스전공, 2017·2020 입학연도, 영어 수준 BASIC·ENG12·ENG34·FREE를 조합했다.
- 각 조합에 합성 일반학생 5명씩, 총 80명이다. 각 학생에게 서로 다른 수강내역 30개를 배정했다.
- 공통교양 fixture의 영어 수준별 과목을 합친 후 실제 repository 쿼리가 수준에 따라 필터링하도록 했다.
- 운영 데이터의 최신성·전체성을 보장하지 않는다. 특히 데이터사이언스 기초학문교양 매핑은 이 fixture에 없다.
- 편입·복수전공·연계전공은 이번 성능 시나리오에 포함하지 않았다.
- `/api/v1/graduations/detail`의 5개 영역을 동일 비율로 조회했다. 로그인 지연은 제외했다.
- 각 회차는 캐시 초기화 후 800요청으로 워밍업했다. 워밍업은 성능 표에서 제외했다.
- 실행 순서는 개인/Redis/Caffeine, Redis/Caffeine/개인, Caffeine/개인/Redis로 구성했다.
- 일정 요청률 실험은 종료 경계에서 k6가 추가 예약할 수 있는 1회에 HTTP 요청을 보내지 않아 정확히 4,000건을 유지한다.
- 각 원본 JSON에 데이터 파일 SHA-256, 운영 코드 기준 커밋, 환경과 회차별 SQL·k6 결과를 보관했다.

환경은 Java 21.0.6, Spring Boot 3.3.4, Spring Data Redis 3.3.4, Caffeine 3.1.8,
k6 1.7.1, MySQL 8.0.29, Docker Desktop의 ARM64 개발 머신이다.
Redis는 로컬 `redis:latest` 이미지를 사용했으며, 실제 이미지 ID는 결과 JSON에 기록했다.
Hikari 최대 연결 수는 10이고, JaCoCo 계측은 포함하되 Hibernate SQL 콘솔 출력과 p6spy 로깅은 껐다.
애플리케이션·부하 발생기·DB가 같은 머신에 있으므로 실제 운영 서버의 절대 응답 시간으로 환산하지 않는다.

## 구현과 검증 범위

| 캐시 대상 | 키 조건 |
| --- | --- |
| 공통교양 | 입학연도, 영어 수준 |
| 핵심교양 | 입학연도 |
| 전공 마스터 | 전공 이름 |
| 기초학문교양 | 전공 이름, 입학연도 |
| 선택필수 정책 | 정책 종류, 전공 이름, 입학연도, 주전공·복수전공 구분 |

모든 공유 키에는 테스트용 공개 버전도 포함한다.
사용자 수강내역에 의존하는 `findDuplicatedLecturesBetweenMajors`는 공유 캐시에 넣지 않았다.
변경 가능한 `MajorLecture` 등은 캐시에서 직접 공유하지 않고 스냅샷에서 매 요청 새로 만든다.
Redis는 JVM 내 키별 로딩 잠금, Caffeine은 원자적 `get(key, loader)`를 사용했다.

- 일정 요청률·버스트의 본 측정 43,200건에서 HTTP 오류와 비캐시 기준 응답 불일치가 모두 0건이었다.
- 일정 요청률 실험에서 누락된 예약 요청(`dropped_iterations`)은 0건이었다.
- 학생별 전체 응답을 비교하되 순서가 보장되지 않은 배열은 정규화했다. 이는 캐시 전후 동등성 검사이며 학사 판정 자체의 정답 검증은 아니다.
- 두 실제 저장소 방식 모두 정책 변경 후 커밋 시 새 버전 조회, 롤백 시 이전 버전 유지를 확인했다.
- 개인 수강내역 삭제 후 커밋 시 캐시 삭제, 다른 학생의 내역 유지, 변경 후 HTTP 응답의 비캐시 결과 일치를 확인했다.
- 별도 단위 테스트 9개에서 빈 결과, 키 분리, 32개 동시 로딩, 로딩 실패 후 재시도, 구버전 로딩과 새 버전의 경합, 가변 객체 격리를 검증했다.
- 최종 회귀 실행에서 기존 관련 72개와 새 단위 테스트 9개, 총 81개가 통과했다. 환경변수 없이 실행한 벤치마크 2개는 의도대로 건너뛰었다.

갱신 검증에는 테스트 전용 커밋 후 공개·무효화 훅을 사용했다.
기존 운영 파싱·과목 추가·삭제 경로의 무효화 타이밍을 수정한 것은 아니다.
공개 버전과 중복 로딩 잠금은 한 JVM 범위이며, 분산 버전 전파·모든 DB 트랜잭션 경합·Redis 장애 대체 처리는 검증하지 않았다.
운영 적용에는 이 갱신 경로 연결과 장애 검증이 추가로 필요하다.

## 재실행과 원본

Docker, Java 21, k6가 필요하다. 벤치마크는 명시적 환경변수가 있을 때만 실행된다.

```sh
# 일정한 요청률
SHARED_CACHE_BENCHMARK=true ./gradlew test --tests '*SharedMasterCacheBenchmarkTest' --rerun-tasks --no-daemon

# 100 VU 버스트
SHARED_CACHE_BENCHMARK=true SHARED_CACHE_WORKLOAD=burst ./gradlew test --tests '*SharedMasterCacheBenchmarkTest' --rerun-tasks --no-daemon

# 빠른 캐시 단위 테스트
./gradlew test --tests '*SharedMasterCacheTest' --no-daemon
```

테스트가 만든 MySQL·Redis 컨테이너와 임시 합성 JWT 파일은 종료 시 정리한다.
기존 로컬 컨테이너는 종료하거나 변경하지 않는다.

최종 성공 결과:

- 일정 요청률: `build/reports/benchmarks/shared-master/2026-09-13T15-41-17.555411Z/report.json`
- 버스트: `build/reports/benchmarks/shared-master/2026-09-13T15-46-20.793707Z/report.json`
- 각 폴더에 회차별 k6 JSON과 로그가 있다. `prime-*`, `*-warmup`은 본 측정에서 제외한다.
- `15-37-25` 실행은 Redis 메모리 수집 오류, `15-39-06` 실행은 k6 종료 경계의 추가 iteration 판정 오류로 중단된 진단 실행이다. 성능 표에서 제외했다.

기존 `DEV-113_캐시_기준선_측정.md`의 87.2ms / 70.5ms 결과와는 학생 데이터, 과목 매핑,
요청 분포, 부하 발생 방식이 다르다. 서로 다른 실험의 숫자를 개선 전후로 연결하면 안 된다.

[Caffeine 원자적 로딩](https://github.com/ben-manes/caffeine/wiki/Population).
