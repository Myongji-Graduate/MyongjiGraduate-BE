# DEV-113: 졸업요건 상세 조회 캐시 기준선 측정

- 측정일: 2026-09-14 (KST)
- 브랜치: `feature/DEV-113`
- 대상 커밋: `529003b`

운영 코드를 수정하지 않고 테스트 전용 설정에서 기존 개인 Redis 캐시 사용/미사용을 비교했다.
공유 졸업요건 캐시는 이번 실험에서 구현하거나 측정하지 않았다.

## 실행 결과

기존 졸업 계산, 캐시 무효화, 시간표 추천 관련 테스트 72개가 통과했다.
별도 HTTP 벤치마크 1개도 통과했다.

| 모드 | 측정 요청 | 평균 응답 시간 | 회차별 평균 범위 | 회차별 p95 범위 | SQL / 500요청 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 개인 캐시 미사용 | 1,500 | 87.15ms | 77.97~103.41ms | 137.14~184.36ms | 1,800 |
| 기존 개인 Redis 캐시 사용 | 1,500 | 70.55ms | 56.67~87.31ms | 122.86~170.07ms | 1,300 |

- 각 모드 500요청씩 3회 측정했다. 요청 수가 같으므로 세 평균의 평균은 전체 1,500요청의 평균과 같다.
- p95는 회차별 범위이며, 전체 요청을 합친 p95로 해석하면 안 된다.
- 이번 실행의 평균 지연시간은 약 19.1%, SQL 횟수는 약 27.8% 감소했다.
- 측정 요청 3,000건에서 HTTP 오류 0건, 캐시 미사용 기준 응답과의 불일치 0건이었다.
- Redis 사용 측정은 회차마다 적중 500회, 미적중 0회였다. 워밍업된 개인 캐시 조건의 결과다.

## 반복 조회 확인

캐시 사용 상태에서 상세 조회 500회가 실행한 SQL은 다음과 같다.

| 조회 대상 | SQL 횟수 |
| --- | ---: |
| 사용자 | 500 |
| 수강과목 | 0 |
| 공통교양 마스터 | 100 |
| 핵심교양 마스터 | 100 |
| 기초학문교양 마스터 | 100 |
| 전공과목 마스터 | 200 |
| 선택필수 정책 | 300 |
| 합계 | 1,300 |

개인 캐시를 끄면 수강과목 조회 500회가 추가되어 1,800회가 된다.
같은 전공과 입학연도여도 마스터 조회가 계속 반복된다.
선택필수 정책은 이번 합성 데이터에 등록하지 않았으므로, 300회 모두 빈 결과를 반환하는 조회다.

| 상세 영역 | 개인 캐시가 비어 있을 때 | 같은 사용자 재조회 | 같은 조건의 다른 사용자 첫 조회 |
| --- | ---: | ---: | ---: |
| 공통교양 | 3 | 2 | 3 |
| 핵심교양 | 3 | 2 | 3 |
| 전공필수 | 4 | 3 | 4 |
| 전공선택 | 4 | 3 | 4 |
| 기초학문교양 | 4 | 3 | 4 |

SQL 횟수는 Hibernate StatementInspector로 수집했다. 바인딩 값이나 개인정보는 기록하지 않는다.
이는 SQL 요청 횟수이며, 각 쿼리가 차지하는 DB 실행시간이나 병목 비중을 측정한 값은 아니다.

## 환경과 시나리오

- Java 21.0.6, Spring Boot 3.3.4, 실제 HTTP 서버의 임의 로컬 포트.
- MySQL 8.0.29와 Redis는 Testcontainers가 만든 별도 컨테이너를 사용했다.
- Docker Desktop, 애플리케이션, k6가 같은 ARM64 개발 머신에서 실행됐다.
- HikariCP 최대 연결 10개, 기존 JDK 직렬화 및 개인 캐시 TTL 10분을 사용했다.
- JUnit 실행에는 JaCoCo 계측이 포함되므로 운영 환경의 절대 응답시간으로 환산하지 않는다.
- Hibernate SQL 콘솔 출력과 p6spy 로깅은 끄고 측정했다.
- 합성 일반학생 20명: 영어영문학전공, 입학연도 2020, 영어 수준 ENG12.
- 합성 강의 160개: 공통교양 20, 핵심교양 40, 기초학문교양 20, 전공 80.
- 학생별 서로 다른 수강과목 47개. 실제 성적표나 운영 DB 데이터를 사용하지 않았다.
- k6 가상 사용자 100명, 각 5회 요청. 5개 상세 영역을 결정적으로 순환하여 각 영역 100회씩 호출했다.
- 매 회차 캐시 초기화 후 500회 워밍업하고, 이후 500회를 측정했다. 모드 순서는 미사용/사용/사용/미사용/미사용/사용이다.
- 합성 사용자별 미사용 응답을 기준으로 매 응답을 비교했다. 순서가 보장되지 않는 배열은 순서를 정규화했다.
- 테스트에서 발급한 합성 사용자 JWT를 사용하므로 로그인 API의 지연시간은 집계에 포함되지 않는다.
- 이 비교는 캐시 적용 전후 결과 동등성을 검사하며, 합성 데이터의 학사 규정 적합성 전체를 검증한 것은 아니다.

사용한 이미지 ID:

```text
mysql:8.0.29 sha256:02662e079c08f45f90a837cf583cfb18bc58a400342d4fefde11199f3d1f4102 arm64
redis:latest sha256:3b0f54bf27a77c98d319dc3a6706ed500a8985309f0b6c6407599b869f4a2bd9 arm64
```

`redis:latest`는 고정 버전 태그가 아니므로 재실행 시 이미지 ID도 비교해야 한다.

## 재실행

Docker, Java 21, k6가 필요하다. 벤치마크는 환경변수를 명시한 경우에만 실행된다.

```sh
GRADUATION_BENCHMARK=true ./gradlew test --tests '*GraduationDetailBenchmarkTest' --rerun-tasks --no-daemon
```

`--rerun-tasks`는 이전 테스트 결과가 최신으로 판단되어 벤치마크 실행이 생략되는 것을 방지한다.

기존 관련 테스트 실행:

```sh
./gradlew test --tests '*Calculate*ServiceTest' --tests '*TakenLectureCacheEvictTest' --tests '*RecommendBeforeTimetableServiceTest' --tests '*RecommendAfterTimetableServiceQueryCountTest' --no-daemon
```

테스트는 임시 JWT 파일을 삭제하고 Redis 컨테이너를 종료한다.
MySQL은 테스트 JVM 종료 시 Testcontainers가 정리한다. 기존 로컬 DB와 운영 DB는 변경하지 않는다.

파일:

- `src/test/java/com/plzgraduate/myongjigraduatebe/benchmark/GraduationDetailBenchmarkTest.java`
- `src/test/resources/application-benchmark.properties`
- `src/test/resources/benchmark/graduation-detail.js`
- 이번 최종 원본 결과: `build/reports/benchmarks/graduation/2026-09-13T15-12-31.592387Z/report.json`
- 같은 폴더에 회차별 k6 JSON과 로그가 있다. `*-warmup.json`은 측정 결과에서 제외한다.

앞선 `2026-09-13T15-10-04.217992Z` 실행은 SQL 콘솔 출력이 켜진 진단 실행이므로 위 성능 표에 포함하지 않았다.

## 판단

기존 개인 캐시는 이번 조건에서 수강과목 반복 조회를 제거했다.
공유 마스터와 선택필수 정책의 반복 조회도 확인되어 다음 캐시 실험의 대상으로 삼을 근거가 있다.
다만 공유 캐시가 실제 지연시간이나 운영 DB 부하를 얼마나 줄이는지는 별도 구현과 비교 측정이 필요하다.

이번 결과는 한 학과의 일반학생, 워밍업된 캐시, 짧은 동시 요청 구간에 한정된다.
복수전공, 편입, 콜드 캐시 폭주, 데이터 갱신 경합, 운영 트래픽의 캐시 적중률을 대표하지 않는다.
따라서 기존 포트폴리오의 "공유 캐시 적용으로 200~500ms에서 15~30ms 개선"이나
"동시 요청에도 DB 조회 최초 1회"를 뒷받침하는 결과로 사용하면 안 된다.
