# DEV-113 공유 캐시 운영 적용 및 비교 절차

## 범위

9월 14일 비교 실험과 별도로, 운영 포트에 Redis 공유 캐시를 연결한다.
공통교양, 핵심교양, 전공, 기초학문교양, 선택필수 정책이 대상이다.
개인 수강내역에 의존하는 중복 전공 과목 조회는 공유하지 않는다.
기존 개인 캐시 설정, 저장 형식, 무효화 경로는 변경하지 않는다.

공유 캐시의 기본값은 OFF다. 기존 Redis 연결을 사용하며 새 서버나 런타임 의존성을 추가하지 않는다.
기존 미커밋 Caffeine 의존성은 과거 비교 실험용이며 운영 캐시에 필요하지 않다.
이 구현을 운영에 적용했다고 해서 과거 실험의 성능 수치를 운영 성과로 사용할 수는 없다.

## 설정

| 환경 변수 | 기본값 | 의미 |
| --- | --- | --- |
| `SHARED_MASTER_CACHE_ENABLED` | `false` | 공유 캐시 사용 여부. 변경 후 재시작 필요 |
| `SHARED_MASTER_CACHE_NAMESPACE` | 빈 값 | 활성화 시 필수. `dev`, `prod`처럼 환경별로 분리 |
| `SHARED_MASTER_CACHE_VERSION` | 자동 생성 | 배포 시스템이 주입하는 배포 ID. 비워두면 앱 기동마다 UUID 생성 |

namespace와 명시적으로 지정한 version에는 영문, 숫자, 점, 밑줄, 하이픈만 허용한다.
ON인데 namespace가 없거나 version의 형식이 잘못됐으면 기동에 실패한다.
version을 생략한 것은 오류가 아니다. `startup-<UUID>`를 생성하고 기동 로그에 namespace와 version을 기록한다.
캐시가 OFF면 버전을 만들거나 Redis 공유 캐시를 조회하지 않는다.

개발 서버의 첫 비교 예시:

```text
SHARED_MASTER_CACHE_ENABLED=false
SHARED_MASTER_CACHE_NAMESPACE=dev
```

같은 이미지와 DB에서 `SHARED_MASTER_CACHE_ENABLED=true`로 바꾸어 재시작한다.
Render에서는 version 환경변수를 설정하지 않는다. 기존에 고정값을 설정했다면 제거한다.
버전이 생략된 경우 재배포, 같은 커밋 재배포, 앱 재기동 모두 새 캐시 공간을 사용한다.
이는 전체 인스턴스 설정이며 테스트 사용자만 선택하는 플래그가 아니다. 개발 환경부터 검증한다.
Render의 dev 환경은 PostgreSQL을 사용하므로 Redis 접속 환경 변수도 별도로 확인해야 한다.
운영 EC2와 Render의 성능 수치를 직접 비교하지 않는다.

키는 `graduationMaster:v1:<namespace>:<version>::<JSON 조회 조건>`이다.
TTL은 24시간이고 기존 `takenLectures` 키와 분리된다. 저장 형식은 JDK 직렬화이며,
스냅샷의 호환성이 바뀌면 코드의 `v1` 스키마 접두어도 변경한다.
캐시에 학생 ID, 이름, 성적표를 저장하지 않는다.

## 배포별 자동 교체

- 운영 GitHub Actions는 `gha-<run_id>-<run_attempt>`를 이미지 태그와 캐시 버전으로 함께 사용한다.
  같은 커밋의 새 실행이나 워크플로 재실행도 새 ID를 받는다. 배포는 고유 태그 이미지를 사용하며
  호환용 `v2` 태그도 계속 발행한다. 배포 실행은 concurrency 그룹으로 직렬화한다.
- 운영 ON/OFF는 GitHub Actions repository variable `SHARED_MASTER_CACHE_ENABLED`로 제어한다.
  미설정 시 `false`, 활성화 시 `true`로 설정한 뒤 배포한다. 실제 저장소 변수는 이번 작업에서 바꾸지 않았다.
- 운영 namespace는 `prod`로 주입된다. 사용자가 매 배포마다 version을 입력할 필요는 없다.
- Render는 앱 기동 시 자동 버전을 생성한다. 여러 복제본은 서로 다른 캐시 공간을 사용한다.
  여러 인스턴스가 동일 캐시를 공유해야 한다면 향후 배포 시스템에서 동일한 새 배포 ID를 주입한다.
- 운영에서 기존 컨테이너가 단순 재시작되면 주입된 ID를 유지한다. 이는 새 배포가 아니다.
  배포 없이 DB를 수정한 후 단순 재시작하는 것으로 캐시 갱신을 보장할 수 없다.
- Redis가 실행 중이면 재시작하거나 삭제하지 않는다. 중지된 경우 시작하고, 없는 경우에만 생성한다.
  Redis가 준비되지 않거나 이미지 다운로드가 실패하면 기존 앱 컨테이너를 유지한 채 배포를 중단한다.
- 기존 배포 스크립트의 볼륨 삭제 및 전체 prune은 제거했다. 디스크 부족은 별도 운영 조치가 필요하다.
  배포별 고유 태그 이미지가 쌓이므로 보존할 릴리스 수와 이미지 정리 정책도 별도로 관리한다.
- 새 앱의 Docker healthcheck가 통과해야 배포 성공으로 처리한다. 기동이나 Flyway 마이그레이션 실패 시
  성공으로 보고하지 않는다. 새 앱으로 교체한 뒤 실패한 경우 자동 롤백은 제공하지 않는다.

## 정합성과 데이터 갱신

조회 조건은 기존 실험과 같다. 공통교양은 입학년도와 영어 수준, 핵심교양은 입학년도,
전공은 전공명, 기초학문교양은 전공명과 입학년도, 선택필수는 종류·전공명·입학년도·전공 유형이다.
불변 스냅샷을 저장하고 요청마다 새 도메인 객체를 만들어 학생별 계산의 변경 상태를 격리한다.
빈 목록도 캐시하며, 트랜잭션 중 조회한 새 값은 커밋 후에만 저장한다. 롤백 시에는 저장하지 않는다.

현재 대상 마스터 데이터는 조회 포트와 마이그레이션으로 관리되며 실시간 수정 API는 없다.
자동화 대상은 배포 시 캐시 교체다. 임의의 SQL 변경 감지나 온라인 정책 공개 기능은 제공하지 않는다.
운영에서 마스터 데이터 또는 조회 규칙을 변경할 때는 다음 순서를 따른다.

1. 코드와 필요한 Flyway 마이그레이션을 같은 배포 변경으로 검토하고 테스트한다.
2. 운영 워크플로가 새 이미지를 받은 뒤 기존 단일 앱을 종료하고 새 배포 ID로 기동한다.
3. 새 앱은 Flyway 마이그레이션을 거쳐 기동하며, 실패하면 건강한 배포로 처리되지 않는다.
4. 첫 조회부터 새 버전 공간에 값을 채운다. 구 키는 사용하지 않으며 마지막 저장 후 24시간 TTL로 만료된다.

운영은 현재 단일 앱 교체 방식이며 이 과정에 서비스 중단 시간이 있다.
Render 개발 환경은 Flyway가 비활성화되어 있으므로 배포만으로 데이터 마이그레이션이 실행되지는 않는다.
개발 DB의 데이터 변경은 별도 검증·적용 절차가 필요하다.

배포 외 직접 SQL 변경이나 구 인스턴스가 살아 있는 롤링 배포에서는 먼저 모든 관련 앱의 공유 캐시를 OFF로
전환하고 구 요청 종료를 확인한 뒤 데이터를 변경한다. 검증 후 새 배포로 다시 ON한다.
TTL 만료만 기다리면 변경 전 데이터가 노출될 수 있다.

앱 롤백도 새 배포 실행으로 수행한다. DB 마이그레이션은 앱 롤백으로 자동 복구되지 않으므로 호환성을 별도 확인한다.
데이터를 되돌릴 때도 먼저 OFF로 전환하고 검증 후 새 ID로 배포한다. 예전 ID를 직접 재사용하지 않는다.
새 수정 API나 자동 갱신 작업을 추가할 때는 이 절차를 재검토하고 커밋 후 분산 버전 공개를 구현해야 한다.
`FLUSHDB`, `FLUSHALL`, 전체 개인 캐시 삭제는 사용하지 않는다.

## 장애와 관측

- 공유 캐시 읽기·역직렬화·쓰기 실패 시 DB 조회 결과를 사용한다. DB 자체 실패는 그대로 전달한다.
- 캐시 실패 후 5초 동안 해당 JVM에서 공유 캐시 접근을 생략하고 이후 재시도한다.
- 최초 실패 요청은 Redis 타임아웃까지 기다릴 수 있다. 개발 배포에서
  `SPRING_DATA_REDIS_TIMEOUT`을 명시하고 실제 장애 응답시간을 확인한다.
- 기존 개인 캐시와 인증의 Redis 장애 처리는 바꾸지 않았다. Redis 전체 장애에도 API가 성공한다는 보장은 아니다.
- 같은 키의 중복 로딩 잠금은 한 JVM 범위다. 트랜잭션 커밋 전에 겹치는 미적중과 여러 인스턴스의 미적중은
  중복 DB 조회가 가능하다. 분산 환경에서 DB 조회 1회를 보장하지 않는다.
- Micrometer `graduation.master.cache` 카운터에 `outcome=hit|miss|load|error|bypass`를 기록한다.
  Prometheus에서는 `graduation_master_cache_total`로 확인한다. 사용자나 키를 지표 태그로 넣지 않는다.
- 지표 수집·장기 보관은 별도 설정이다. 이번 변경은 수집 서버나 AWS 유료 리소스를 만들지 않는다.

## 로컬 검증

```sh
./gradlew test --tests '*GraduationMasterCache*' --no-daemon
./gradlew test --tests '*ProductionDeploymentWorkflowTest' --no-daemon
```

설정 OFF/ON 및 잘못된 설정의 기동 실패, 자동 버전 생성, 조회 조건 분리, 빈 결과, 동시 로딩,
공유 캐시 장애 시 DB 복귀와 재시도, DB 예외 전파, 커밋·롤백, 가변 객체 격리를 검사한다.
Redis 통합 테스트는 Testcontainers의 독립 Redis를 사용해 24시간 TTL, 환경·버전 분리,
5종 포트의 직렬화 왕복과 캐시 적중, 개인별 쿼리 제외, 자동 버전 교체 시 개인 키 보존을 검증한다.
Docker가 없으면 Redis 통합 테스트는 건너뛰므로 결과에서 skipped 수를 반드시 확인한다.
배포 워크플로 테스트는 실제 YAML의 SSH 스크립트를 가짜 Docker·sleep 명령으로 실행한다.
실제 서버에 접속하지 않고 Redis 유지·최초 생성·기동, 준비 실패, 이미지 다운로드 실패,
앱 healthcheck 실패 및 잘못된 플래그 처리를 확인한다. 실제 원격 배포 검증을 대신하지는 않는다.

2026-09-26 자동 버전 연결 후 로컬 검증 결과:

- 공유 캐시 테스트 21개(실제 Redis 통합 테스트 6개 포함), 배포 모의 실행 테스트 8개 모두 통과했다.
- `./gradlew test --no-daemon`: 총 774개 중 772개 통과, 실패 0개, 기존 수동 실행 벤치마크 2개 건너뜀.
- 활성화된 캐시의 Spring 포트 선택과 Redis 연동은 검증했다. 배포 환경의 HTTP OFF/ON 비교 및
  운영 코드의 부하 성능 재측정은 아직 하지 않았다. 9월 14일 실험 수치를 이번 구현의 실측값으로 대체하지 않는다.

## 배포 후 비교

1. 개발 서버에 OFF로 배포하고 실제 커밋과 기동 상태를 확인한다. PR 머지 여부와 배포 완료는 별개다.
2. 고정된 합성 테스트 계정으로 동일 API·요청 비율을 사용한다. 개인정보나 운영 계정을 재사용하지 않는다.
3. OFF/ON 양쪽 모두 재시작 후 같은 준비 시간과 워밍업을 둔다. 로그인 시간은 제외한다.
4. 적은 요청률부터 시작하고 사전에 요청량·실행 시간·오류율·지연·자원 사용 중단 기준을 정한다.
5. 같은 조건에서 각 3회 이상 번갈아 측정한다. 평균·회차별 p95·오류율·응답 동등성,
   캐시 카운터 증분, CPU, DB 연결 대기를 보관한다. SQL은 테스트 요청을 구분할 수 있을 때만 집계한다.
6. 새 배포는 공유 캐시가 비어 있는 상태로 시작하지만 개인 캐시는 유지된다. 콜드 테스트는 전용 계정과
   캐시 종류별 초기 상태를 명시하고 웜 캐시 결과와 섞지 않는다. 운영 전체 캐시를 초기화하지 않는다.

측정값은 배포 환경에서의 합성 요청 결과로 명시하며 실제 사용자 트래픽 개선과 구분한다.
이번 작업은 코드와 로컬 검증까지만 수행한다. 원격 테스트, 배포, PR 생성은 별도다.
