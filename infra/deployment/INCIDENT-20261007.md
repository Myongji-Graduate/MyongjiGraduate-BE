# 2026-10-07 OCI 운영 응답 중단 및 복구

시간은 KST이며, 최초 원인과 복구 과정에서 확인한 문제를 구분한다.

## 확인한 증상과 증거

- SSH/8080 TCP 연결은 성립했지만 SSH 배너와 HTTP 응답이 도착하지 않았다.
- OCI는 Running이었다. 자원 차트는 09:45 이후 갱신되지 않았다. 마지막 CPU 1.172%, 메모리 84.53%는 장애 당시의 실시간 수치로 해석할 수 없다.
- 이전 부팅의 09:46 이후 Docker healthcheck 시작 지연, containerd event timeout, 이후 SSH/systemd 로그인 세션 timeout이 기록됐다.
- 이전 부팅 커널 저널 검색에서 OOM kill, kernel panic, soft lockup 기록을 찾지 못했다. 로그 부재로 메모리 압박을 배제할 수는 없지만 OOM 발생으로 확정하지 않는다.
- VM RAM 956 MiB, swap 없음, 앱 컨테이너 메모리 제한/JAVA_OPTS 없음이었다. 메모리 압박은 가능한 원인이지만 최초 정지 원인은 미확정이다.
- 재부팅 후 Autoheal이 10:34:09 앱을 unhealthy로 판단해 시작 도중 재시작했다. 기존 건강 검사 유예는 40초였고 기존 기동 관찰은 3~4분이었다. 이 문제는 복구를 지연시키는 확인된 요인이다.
- IntelliJ가 사용하던 로컬 13306 SSH 터널도 종료된 상태였다. 이 연결은 운영 VM을 경유하므로 VM 장애의 영향을 함께 받는다.

## 적용한 복구

1. OCI 강제 재부팅 후 SSH 복구. 현재 부팅 시작 10:31:34.
2. Autoheal을 잠시 멈추고 기존 운영 이미지 `stophwan/mju-graduate-server:gha-37437770386-1`를 유지하며 앱 컨테이너를 재생성했다.
3. 앱 memory 640 MiB, reservation 512 MiB, memory+swap 합계 1 GiB; JVM heap 64~256 MiB, ActiveProcessorCount=2.
4. 건강 검사: 시작 유예 300초, 주기 30초, timeout 10초, curl max-time 8초, 재시도 5회.
5. 기존 디스크에 1 GiB swap과 swappiness=10을 설정해 재부팅 후에도 유지한다.
6. 앱 정상 시작 후 기존 Autoheal을 다시 켰다.
7. 1분마다 load, 가용 메모리, swap, CPU/memory/I/O pressure 수치만 기존 시스템 저널에 기록한다. 새 유료 클라우드 리소스는 만들지 않았다.
8. 사용자 맥에 기존 SSH 키를 사용하는 로컬 DB 터널 자동 재연결을 설정했다. IntelliJ 주소는 127.0.0.1:13306을 유지한다. 백그라운드 Documents 접근 제한을 피하도록 키의 로컬 사본을 표준 SSH 폴더에 권한 600으로 보관했다. 키/비밀번호는 저장소에 포함하지 않는다.

## 검증 결과

- 앱 시작 104.497초, health=healthy, restart=0, OOMKilled=false.
- Autoheal health=healthy, restart=0.
- 외부 actuator health HTTP 200 / UP, Swagger HTML HTTP 200 및 브라우저 API 목록 렌더링 확인.
- API 문서 실제 경로는 `/api-docs`이다. `/v3/api-docs`는 이 프로젝트에 없는 경로다.
- 로컬 터널 MySQL protocol 10 응답과 IntelliJ `SELECT 1 AS connection_ok`의 값 1을 확인했다. 운영 개인정보를 조회하지 않았다.
- 배포 흐름 JUnit 8개, Autoheal Python 테스트 8개 통과.
- 호스트 준비 스크립트 반복 적용과 일반 SSH 사용자·표준 입력 방식 실행도 성공했다. swap은 기존 파일을 유지했다.
- 운영 부하 시험은 수행하지 않았다. 256 MiB heap에서 기동 성공만 검증했으며 실제 트래픽에서 필요한 메모리 여유는 추가 관찰 대상이다.

## 다음 배포와 진단

복구 브랜치의 Dockerfile/배포 workflow/호스트 준비 스크립트를 develop과 main에 반영해야 다음 배포에도 앱의 메모리 제한과 시작 유예가 유지된다. 서버에 직접 적용한 swap 및 자원 기록은 이미 지속된다. DEV-116 변경은 포함하지 않는다.

자원 기록: `sudo journalctl -u mju-resource-snapshot.service --since "..."`.
커널 기록: `sudo journalctl -k -b -1`.
기존 앱은 `mju-graduate-server-before-recovery-1791337142`로 정지 보관했고 재시작 정책을 `no`로 설정했다. 서버의 root 전용 `/var/lib/mju-recovery`에는 롤백 설정이 있으며 자격 증명이 포함될 수 있으므로 내용 출력/외부 전송/저장소 추가를 하지 않는다.
